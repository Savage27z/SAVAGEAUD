# Target census — 2026-09-22 (bug-hunting resume: gambling + new protocols)

## Method + honest limits
- DefiLlama `/protocols` for new/small EVM protocols (fields include `tvl`, `listedAt`, `category`,
  `chains`, `address`, `audits`, `audit_links`, `url`, `twitter`).
- **`audits` is a STRING ('0'..'3'), not a list or int.** A truthy test labels every protocol
  "audited" — caught by control against Binance CEX (`'0'`) / Lido (`'2'`). Parse with int().
- **`address` is `chain:0x…`-prefixed and the prefix is LOWERCASE** (`base:0x…`), which breaks a
  title-case chain map. Most protocols carry no address at all.
- **DefiLlama has no Casino/Gambling bucket** (confirmed: only `Yield Lottery` 1, `Prediction Market`
  2, `Gaming` 1 in the size band) and does not index consumer casinos (death.fun/nar.bet class).
- **Dapp directories are walled for scraping**: DappRadar returns a ~28KB challenge page (0 dapp
  slugs) and the Alchemy dapp lists time out under headless Chrome. Not defeated by design.
- **"Best provably fair casino" web results are affiliate listicles** (cryptoslate/cryptocasinos/
  readwrite/coingabble) listing custodial web2 casinos — no contracts, wrong class for a contract audit.
- **Verification checks came back UNCONFIRMED, not "unverified"**: Blockscout returned
  `verified=None` for EntryPoint v0.6 (`0x5ff137d4…`) and v0.7 (`0x0000000071727de2…`), which are
  certainly verified. The check failed its own positive control → rate-limited/broken, so no
  verification verdict from this pass may be used.

## TayDex — first recon result (the live one)
Harvested 9 non-canonical addresses from its bundle; `eth_getCode` says **5 are real contracts on Base**
(bytecode-fragment noise filtered out — the correct discriminator):
- `0x0000000071727de2…` 16,035B — **ERC-4337 EntryPoint v0.7**
- `0x5ff137d4b0fdcd49dca30c7cf57e578a026d2789` 23,689B — **ERC-4337 EntryPoint v0.6**

- `0x4be0ddfebca9a5a4a617dee4dece99e7c862dceb` 8,469B ┐ twin-size pair — likely impl + proxy clone,
- `0x85e23b94e7f5e9cc1ff78bce78cfb15b81f0df00` 8,469B ┘ or the same logic deployed twice

→ TayDex is **account-abstraction based** (v0.6 + v0.7 entrypoints both present), so the payout path
runs through a smart account / paymaster rather than a plain EOA call. That is the surface to audit
next: who initiates the bet, who pays, and whether the payout leg is server-signed.
